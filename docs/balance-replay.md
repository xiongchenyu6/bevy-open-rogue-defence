# 平衡重放的结算顺序

固定时间步长、种子和单线程调度不自动保证跨进程重放一致。烧伤状态曾使用标准库随机哈希表，遍历时生成 SkillStrike；之后真实技能与弹道系统按这些伤害实体处理目标并消耗暴击等随机数。哈希遍历顺序不同，可能改变随机数归属，进一步改变击杀经济和后续构筑。

本轮将烧伤状态改为按 Entity 排序的 BTreeMap，保留伤害、层数、持续时间和触发间隔。其他哈希表仅用于查找或独立状态更新，没有据此批量替换全部容器。

回归测试运行真实 tick_skill_runtime：32 个实际敌人，先后两局按相反顺序插入烧伤，检查按生成实体顺序得到的全部目标与伤害一致、每次伤害 6。完整库测试 565 项通过、0 失败、1 项既有忽略；格式检查和全目标严格 Clippy 通过。

这项测试只覆盖烧伤伤害生成顺序，不证明完整跨进程重放一致。异步资产/场景创建实体及其他共同随机数消费者仍可能引起差异；完整重放需要同一构建、同一配置的独立新存档复跑比较。此前两个构建之间的整局差异不能直接归因为生命数值修改。

正在运行的 `campaign-health-multiplier-fixed` 批次使用修正生命账本后的既有二进制，不包含此烧伤顺序改动；该原批次因机器重启中断；恢复批次通过独立二进制快照固定同一构建，因此可以在后台重编译而不混入不同二进制。

严格比较工具：`python3 tools/compare_balance_replays.py LEFT.jsonl RIGHT.jsonl`。校验同一二进制、身份、压力参数及全部记录的检查点序列，拒绝缺失核心字段、损坏 JSON、非有限数值和丢失检查点；报告首个分歧。相同截尾只算前缀相同，两份实际结束且记录相同才报告完整的已记录重放一致，不证明所有内部状态一致。7 项真实 CLI 测试通过；真实生产日志与自身比较只验证读取格式，不作独立重放证据。

## 技能与随机状态观测

模拟器检查点补充 `skill_ranks_by_id`（按实际技能编号的全部等级）和 `rng_state`（实际 RunRng 状态），用于区别构筑改变与随机数消费分歧。分析工具保留这两项字段，旧记录缺失时留空，不补造数据。这只增加读取和日志，不改变战斗规则。

真实 1200 帧短局读取了 32 项技能等级，两处检查点均满足等级总和与已有 `skill_ranks` 一致；随机状态是有效 uint64，随真实游戏推进改变。该局为截尾，不作通关证据。格式、模拟器严格 Clippy、构建及 5 项批次工具测试通过。正在运行的两次完整重放使用此前固定快照，不包含这两项新增观测；它们不能与此构建混作同一二进制比较。
